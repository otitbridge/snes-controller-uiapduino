# キー変換と最小HIDの検証結果

2026-11-10（日本時間）、P1のホスト上の純粋ロジックテストでL01～L03がPASS、P2では最小HIDのビルド・ホストテスト、全キー解放版と手動単キー版の書き込み・MacでのUSB認識に成功しました。ジャンパ線による単キーの押下・保持・解放もMacでPASSです。iPhone／Deltaは本人の希望で後日確認します。

## P1の条件と証拠

- 実施：Codexがローカルのコマンド実行結果を確認。
- 対象：`firmware/snes_controller/snes_hid_report.h` の12ビット入力から8バイトのHIDレポートへの変換。
- ベースコミット：`112a816`。P1の変更は実行時点で未コミットのため、[実行記録](evidence/p1-host-tests-2026-11-10.json) のソースSHA-256で特定。
- OS／CPU：macOS 26.7.1／Darwin arm64。
- コンパイラ：Apple clang 21.0.0（`c++`）、C++14。`-Wall -Wextra -Werror -pedantic -DNDEBUG` を指定。
- 実行方法：通常の `-O2` と、`-O1`＋AddressSanitizer／UndefinedBehaviorSanitizerの2構成。両方とも終了コード0、警告・sanitizer診断なし。
- バイナリ：`.local/host-tests/hid_report_test` と `hid_report_test_sanitized`。ホスト用実行ファイルであり、MCU用ファームウェアではない。SHA-256は実行記録に保存。
- MCU用のコア／FQBN／USBモード／Flash・RAM使用量：今回のホストテストでは対象外。
- 実物の基板・コントローラー・接続ピン・端末・Delta・ケーブル：今回の試験では使用していない。

再実行コマンド（プロジェクトのルート）：

```sh

SNES_HOST_SANITIZERS=1 bash tests/run_host_tests.sh
```

## 実施したロジック試験

| ID | 条件・手順 | 期待結果 | 実際の結果 |
| --- | --- | --- | --- |
| L01 | 全解放、全12ボタンを各1入力、全ボタン入力を与える。ボタンのビット定義も確認 | 引き継ぎ仕様のUsage ID。modifiers／reservedは0、未使用枠は0 | PASS、通常・sanitizerの両構成 |
| L02 | 下位12ビットの全4096通りを列挙。キーの所属・順序・個数・重複・0埋めを確認 | 押下ボタンのうちbit順の先頭6個だけが出力される | PASS、全4096通り |
| L03 | 7キー→6キーの具体例と、全4096通りの押下状態から1ボタンずつ離す24576通りを確認 | 解放したキーが消え、枠が空けば除外されていた保持キーが現れる | PASS、具体例と全24576通り |

L03の具体例は、右＋B＋Y＋A＋L＋RへSTARTを加えるケースです。7キー時はRが出力枠から外れ、STARTを離すとRが復帰しました。これはレポートのバイト列に対する確認で、DeltaのD05試験は未実施です。

追加で以下を確認しました。

- 全65536通りの `uint16_t` 入力で、上位4ビットを変えても出力が変わらない。
- 単キー・3キー・12キーの入力をそれぞれ3000回与えてもレポートが変わらない。
- 全4096通りで、途中に別の押下状態を挟んでも元の入力に対する結果が変わらない。
- 右＋Y＋BからBだけを離したとき、右とYが残る。全解放で全キー枠が0になる。
- 8バイトのサイズ、各フィールドの位置、コピー可能な構造を確認。
- `Keyboard` というグローバルオブジェクトをテスト側で定義してもコンパイルできる。実際のArduino `Keyboard.h` との統合ビルドはP2で扱う。

3000回の反復は状態の不変性を確認するための呼び出し回数です。実時間の30秒保持、USBでの保持、短押しの最小時間を測ったものではありません。

## P3のSFC診断準備と未接続時の確認

本人から、既存M5StickS3版と同じコントローラーを使い、5信号の接続点を特定済みとの報告を得ました。当初は線色との照合が必要として実配線を延期し、その後、本人からSFC基板1＝茶/GND、2＝赤/DATA、3＝橙/LATCH、4＝黄/CLOCK、5＝白/VCCとの対応が提示されました。[配線表](wiring.md) に本人申告として反映しました。実配線とボタン試験は未実施です。

- 読み取り：最初のビットをCLOCKで進める前に読み、全16ビットのDATA電位を保持。LOWを押下へ反転し、下位12ビットを取り出す。割り込み禁止区間は追加しない。
- ホストテスト：全65,536通りの16ビット入力を、CLOCK立ち上がりでだけ進むシフトレジスタモデルで確認。サンプル順、12µs／6µsの要求値、16回のCLOCK、上位4ビットの保持・マスク、7/8/9のピン設定を確認した。通常とASan／UBSanの両方でPASS。
- 診断API：busy中は共有バッファを上書きせず、次のループで新しい状態を試す。8バイトの固定形式、全解放でのUSB開始、8ビットsequenceの折り返しをホストテストで確認。設定の競合と誤ったUSBモードの4ケースはコンパイルで拒否された。
- ビルド：コア1.2.15は未変更。V1.4／48MHz HSI／`usb=kbdweb`。BIN 5536バイト（`.init` 160＋`.text` 5376）、静的RAM 256バイト。完全なFQBNとSHA-256は [P3記録](evidence/p3-sfc-diagnostic-2026-11-10.json) に保存。
- 互換性：同じソースでビルドした `neutral` と `manual` のBINは、P2で実機確認したSHA-256と一致。元のP2成果物も手元に保持。
- 書き込み：対象1台を照合し、5568バイトの読み戻し一致とアプリ起動を確認。ブートローダの書き換えなし。SFCと単キー試験用ジャンパ線は未接続。
- USB受信：Macでマウス、キーボード、vendor HID（Usage Page `FF00`／Usage `1`、入力8バイト）を確認。Mac用取得コマンドを15秒指定で実行し、1476フレームを受信。不正0件、全フレーム `raw=0xFFFF`／`pressed=0`、連続sequenceの差はすべて1。

初回の単独vendor HID（`usb=webhid`）では書き込み検証に成功した一方、MacにUSBインターフェースが現れず、取得ツールは対象0台で終了しました。その設定の構成記述子は宣言41／実データ34バイトでした。宣言・実データとも84バイトの同梱複合設定へ変更後に受信できました。この差だけを唯一の原因と断定せず、初回の失敗・設定変更・最終結果を記録しています。

未接続での全HIGHはINPUT_PULLUPと整合しますが、SFCが接続されていることや全解放の確認には使えません。**全12ボタンの実物試験、CLOCK／LATCHの実測波形、SFCからのキーボード出力は未確認・未統合です。** 複数キーの共有バッファ対策も次段階です。現在の基板は診断版で、キーボード側は全解放のままです。iPhone／DeltaとSFCの実配線は、本人の希望どおり後日実施します。
